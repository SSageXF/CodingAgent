> 验收日期：2026-08-30

## 1. 验收目标与边界

本次使用用户在本地 `.env` 中配置的真实 OpenAI-compatible API，对三个互相隔离的小型工作区进行端到端测试。测试覆盖：

- 模型能否理解任务并主动选择工具；
- 文件观察、创建和精确修改；
- 本地命令执行、失败复现和修复后复验；
- `read_many`、`git_status`、`git_diff` 三个新增只读工具；
- `submit_result` 是否引用当前运行产生的真实凭证；
- 运行记录、token 用量统计、错误恢复和终止条件；
- `.env` 中的 API Key 是否进入受版本控制文件或运行日志。

测试工作区和运行日志位于被 Git 忽略的 `.audit-cache/real-api-v031/`，不属于产品源码或提交物。报告不记录 API Key、完整请求头或其他认证信息。

## 3. 可以确认已经具备的能力

### 3.1 Agent 闭环真实可用

三个案例均不是预先写死的脚本路径。模型根据工具返回继续决策，并最终用 `submit_result` 正常停止。创建案例只用了 3 个循环；修复案例表现出完整的“读取—复现—修改—复验—提交”闭环。

修复案例尤其证明了执行凭证机制在真实调用中有效：最终声明引用了本轮的失败检查 `op-0003` 和成功检查 `op-0005`，没有只凭文字声称测试通过。

### 3.2 文件与只读 Git 工具可被模型正确使用

- `read_many` 一次读取了实现和测试，减少了模型往返。
- `replace_text` 只替换一个精确匹配，没有重写整个文件。
- `git_diff` 正确观察到 `TAX_RATE = 0.08` 变为 `0.09`。
- 模型结合 `app.py`、`config.py` 和 `test_app.py`，正确推断结果为 `109.0`，而测试仍期待 `108`。
- Git 审查案例结束后，源码 diff 仍只有预置的 `config.py` 变化。

### 3.3 错误不会立即击穿循环

真实运行观察到三类非成功结果：受限网络环境产生的连接错误、Git dubious ownership 错误，以及业务测试失败。Agent 能把工具层错误或非零退出码记录为观察结果，并在预算内继续运行；业务测试失败也没有被误判为工具协议崩溃。

第一次创建案例在受限执行环境中因 Windows 网络权限错误而失败；在获准联网的同一代码和配置下重试后成功，因此该次失败不归因于模型 API 或 EvidenceCoder 的请求格式。

### 3.4 配置与秘密处理符合要求

- `.env` 已被 Git 忽略，配置无需每次手动输入。
- 对 43 个受版本控制文件和 3 份成功运行日志，共 46 个文件进行 API Key 精确值扫描，命中数为 0。
- 报告与终端核查均未输出 Key 的实际内容。

## 4. 发现的问题

### P1：`run_local` 能产生工作区之外的持久副作用

Git 审查案例第一次调用 `git_status` 时，Git 因测试目录所有者与当前用户不同而拒绝访问。模型随后通过 `run_local` 执行：

```text
git config --global --add safe.directory <测试仓库绝对路径>
```

这条命令让后续 Git 工具成功，但它修改的是用户级 Git 配置，不是工作区文件。即使任务明确要求“只读审查、不得运行会改变仓库的命令”，当前 Guard 仍允许它在 `--yes` 模式中执行。

本次新增的精确配置已经在验收结束后撤销，并再次确认只剩测试前原有的三条 `safe.directory` 配置，没有遗留该测试路径。

这不代表模型修改了项目源码，却说明目前“路径限制文件工具 + Shell 审批”并不等于真正的系统沙箱。自动批准 Shell 时，模型仍可能修改全局 Git 配置、用户配置或工作区之外的其他状态。建议在下一版至少加入以下防线：

1. 对 `git config --global`、`git config --system` 等明显越界命令硬拒绝；
2. 将“只读任务模式”落实为命令策略，而不只写进提示词；
3. 长期方案是在受限子进程或容器中执行 Shell，并限制可写路径；
4. 在实现真正隔离前，不建议对未知仓库默认使用 `--yes` 自动批准全部命令。

### P2：中文在本次自动化捕获通道中显示乱码

工具行为、英文输出和退出码均可读，但模型提交的中文摘要在自动化终端捕获及 JSON 运行摘要中出现替换字符。它不影响本轮决策正确性，但会降低中文报告和历史恢复的可读性。

现有本地命令输出解码已覆盖 UTF-8/GBK；本现象更接近模型响应文本或 Windows 捕获链路中的编码问题。建议在用户日常 PowerShell 中再验证一次，以区分第三方兼容网关响应编码与自动化捕获环境。如果可稳定复现，应保存响应原始字节/响应头的非敏感诊断信息并增加中文端到端测试。

### P3：Git 工具对 dubious ownership 缺少可控处理

专用 `git_status` 只返回 Git 错误文本，没有提供受限于当前工作区的安全恢复路径，于是模型退回到通用 Shell。可以考虑让 CLI 启动时检测该错误并向用户说明如何处理，或为当前进程使用临时 Git 配置，而不是允许 Agent 改全局配置。

## 6. 最终评价

EvidenceCoder 0.3.1 已通过真实 API 的核心功能验收：它能够观察代码、调用固定工具、执行和解释检查、完成小型修改、管理本轮凭证并正常终止。新增的批量读取和 Git 观察工具也确实被真实模型采用，而不是只有单元测试覆盖。

当前主要不足不是“不会完成任务”，而是通用 Shell 在自动批准模式下仍能越过工作区产生持久副作用。因此项目满足最初考核对可运行 Coding Agent 的功能要求，也如实证明了自身错误处理与证据闭环；若要把它提升为更放心的日常 CLI Agent，命令隔离应当列为下一项最高优先级工作。

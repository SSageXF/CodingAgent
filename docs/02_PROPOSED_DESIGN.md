# EvidenceCoder 汇总设计稿

> 状态：待审查；不是实现说明，也不代表已经存在可运行代码。

## 1. 产品定义

`EvidenceCoder` 是一个本地运行、单用户、单 Agent 的 Python CLI。用户指定工作区并输入编程任务，Agent 可以检查文件、精确修改代码、执行命令、观察结果并继续迭代。

它的核心特色不是“工具很多”，而是“结论有凭证”：每次本地操作都会得到不可混淆的操作编号，Agent 结束任务时必须引用支持其完成结论的真实操作记录。

## 2. 目标和非目标

### 必须完成

- 原生 tool calling 循环。
- 工作区内的文件列举、分段读取、搜索、精确替换和新建/覆写。
- 本地命令执行、超时、退出码和输出截断。
- 工具参数校验、错误回灌和 API 重试。
- 对话历史、活动上下文和压缩。
- 步数、时间、重复动作、连续失败和用户中断终止。
- 操作记录及带凭证的完成报告。
- 单元测试和一个真实端到端演示任务。

### 明确不做

- GUI、网页、IDE 插件。
- 多 Agent、子 Agent、Planner/Executor 双模型。
- MCP、插件、Skill 或第三方 Agent SDK。
- 向量数据库、Repo Map、Tree-sitter/LSP。
- 自动 Git commit/push。
- 浏览器与联网搜索工具。
- 云端文件、服务端 Code Interpreter。
- 自称拥有 Docker/操作系统级沙箱。

## 3. 技术选择

- Python 3.11+。
- `httpx` 直接请求一个 OpenAI-compatible endpoint。
- 使用模型原生 JSON tool calling。
- `argparse`、`dataclasses`、`pathlib`、`subprocess`、`json` 等标准库。
- 可选 `rich` 只负责终端显示，不参与 Agent 逻辑。
- API Key 从环境变量读取；`.env` 不由程序自动读取，避免误提交。

直接使用 HTTP 而不是 Agent SDK，可以清晰展示请求构造、历史管理、工具解析和重试都是自行实现的。

## 4. 独立控制流

每次循环固定经历六个阶段：

```text
COMPOSE  →  ASK  →  CHECK  →  AUTHORIZE  →  ACT  →  ASSESS
   ↑                                                   │
   └──────────── 需要继续时写入记录簿并回到开头 ───────┘
```

- `COMPOSE`：从运行记录簿投影本次模型上下文。
- `ASK`：调用模型并接收最终文本或工具调用。
- `CHECK`：验证工具名、JSON 参数、数据类型和路径形态。
- `AUTHORIZE`：依据工具风险和命令内容决定自动执行、询问或拒绝。
- `ACT`：执行工具并生成结构化操作记录。
- `ASSESS`：检查完成凭证、预算、重复行为和错误次数，决定继续或终止。

这是一个普通的显式循环，不使用事件总线、框架回调、可插拔中间件或隐藏状态机。

## 5. 数据模型

### OperationRecord

每次工具调用生成一条记录：

```text
op_id            单调递增，如 op-0012
cycle            第几轮模型调用
tool             工具名
arguments_digest 参数摘要，不在日志中泄露大段内容
status           ok / error / denied / timeout
summary          给模型看的短结果
evidence         路径、退出码、哈希、匹配数等机器事实
started_at       开始时间
duration_ms      耗时
```

### RunBook

`RunBook` 是本次任务的内存记录簿，按顺序保存：用户任务、模型响应摘要和 `OperationRecord`。它不是发布订阅 EventStream，也不驱动组件；只有 Engine 可以追加，ContextWindow 只能读取投影。

运行结束后可选保存为 `.evidencecoder/runs/<run-id>.jsonl`，该目录默认加入 `.gitignore`。

### CompletionReport

模型通过 `submit_result` 工具提交：

```text
summary       做了什么
changed_files 变更文件
checks        声称完成的验证
evidence_ids  支撑上述结论的 op_id
limitations   未完成或无法确认的事项
```

Engine 检查 `evidence_ids` 是否存在、是否成功，以及其中是否包含与变更和测试声明相符的记录。检查失败时不会结束，而是把原因作为工具错误反馈给模型。

## 6. 模块规划

```text
evidencecoder/
├─ __main__.py          # CLI 入口和参数
├─ engine.py            # 六阶段循环；唯一的流程所有者
├─ api_link.py          # HTTP 请求、流/非流响应解析、重试
├─ runbook.py           # OperationRecord 与只追加记录
├─ context_window.py    # 从 RunBook 构造活动上下文
├─ guard.py             # 路径规则、工具风险、命令审批
├─ completion.py        # 完成报告和凭证一致性检查
├─ toolbox.py           # 固定工具表、schema 校验、调用分派
├─ tool_impl/
│  ├─ files.py          # 工作区文件操作
│  └─ commands.py       # 子进程执行
├─ display.py           # 终端输出；不含业务状态
└─ settings.py          # 环境变量和运行预算
```

模块名和边界刻意避开参考仓库的 `Agent/Environment/Model`、`Coder`、`AgentController/EventStream/Runtime`、`Session/Turn/ToolRouter`、`Exchange/Extensions` 等组合。

## 7. 固定工具集合

| 工具 | 用途 | 默认策略 |
|---|---|---|
| `inspect_tree` | 列举工作区文件，支持深度和数量限制 | 自动 |
| `read_segment` | 按行读取文本文件 | 自动 |
| `find_matches` | 使用 `rg` 搜索；不可用时 Python 回退 | 自动 |
| `replace_text` | 要求旧文本唯一匹配后精确替换 | 询问或配置自动 |
| `write_text` | 新建文件或明确覆写整文件 | 询问 |
| `run_local` | 在工作区 cwd 执行命令 | 询问；只读白名单可自动 |
| `submit_result` | 提交带凭证的完成报告 | 自动校验，不直接执行外部动作 |

不单独提供 delete、Git、网络或任意目录工具。

## 8. 文件边界

所有文件工具执行以下步骤：

1. 把用户参数相对于工作区根目录解析。
2. 使用规范化绝对路径处理 `..`。
3. 解析已有父目录和符号链接。
4. 验证结果仍位于工作区根目录下。
5. 拒绝目录、设备文件和超出大小限制的文本。
6. 写入前保留旧内容摘要，写后记录 SHA-256。

注意：这些规则只约束内置文件工具。Shell 可以自行访问工作区外路径，因此 Shell 必须通过审批和命令策略控制，不能宣传成强沙箱。

## 9. Shell 策略

- 固定 cwd 为工作区。
- 每次执行是独立子进程，不保留隐式 Shell 会话。
- 默认超时 60 秒，可由 CLI 在安全范围内调整。
- 合并记录 stdout/stderr，并保留退出码。
- 给模型的输出限制字符数，显示头尾并标记截断。
- 明确拒绝关机、格式化磁盘、递归删除工作区外路径、提权和 Git 历史改写等命令。
- `--yes` 只能跳过普通写入/命令确认，不能跳过硬拒绝规则。
- 终端确认展示原始命令，不让模型伪造“已批准”。

## 10. 上下文管理

### 正常窗口

发送给模型的内容按以下顺序组成：

1. 自行编写的系统提示：角色、工具约束、完成凭证要求。
2. 原始用户任务。
3. 当前工作区事实表：已读文件、已改文件、最近命令及结果。
4. 最近若干轮完整模型消息和工具结果。
5. 较早历史的压缩摘要（若存在）。

### 工具输出控制

- 文件读取强制行数上限。
- 搜索强制匹配数上限。
- 命令输出在进入历史前截断。
- RunBook 可保存完整本地结果摘要，但活动提示只取必要字段。

### 压缩

估算上下文达到阈值时，由同一模型执行一次独立的摘要请求，把较早记录压缩为固定 JSON：目标、已确认事实、已改文件、失败尝试、未完成事项。摘要通过 schema 校验后替换活动窗口中的旧记录；原始 RunBook 不删除。

若摘要失败，退化为确定性事实表加最近窗口，不让压缩错误摧毁任务。

## 11. 错误语义

所有可预期错误都转为结构化结果反馈给模型：

- API 429/5xx/超时：指数退避，最多 3 次。
- 非法 tool call：说明允许工具和具体参数问题。
- 文件不存在或编码失败：返回错误，不抛出整个程序。
- 精确替换零匹配或多匹配：拒绝修改并要求重新读取。
- 命令非零退出：属于有效观察，不等同于程序异常。
- 命令超时：标记 timeout，并继续由模型决定替代方案。
- 连续 3 次 API/协议错误：终止并向用户报告。

## 12. 终止条件

- `submit_result` 通过凭证校验。
- 达到最大模型轮数，默认 30。
- 达到墙钟时间，默认 20 分钟。
- 连续 3 次相同工具、相同参数、相同结果指纹。
- 连续 5 次工具错误且没有成功操作。
- 用户按 Ctrl+C。
- API 连续失败或认证失败。

终止报告必须区分 `completed`、`budget_exhausted`、`stalled`、`cancelled` 和 `failed`。

## 13. 测试方案

### 单元测试

- 路径穿越、符号链接越界和大小限制。
- `replace_text` 的零/单/多匹配行为。
- 命令成功、失败、超时和输出截断。
- tool call JSON/schema 错误。
- API 重试与不可重试认证错误。
- 上下文窗口投影和摘要失败回退。
- 重复动作与所有终止原因。
- 完成凭证缺失、引用失败记录、测试声明不匹配。

### 确定性循环测试

使用本地 FakeModel 按预设顺序返回工具调用，无需真实 API 即可测试完整循环。FakeModel 只用于测试，不属于运行时 Agent 框架。

### 端到端演示

准备一个小型 Python 项目，其中有一个边界条件 bug 和失败测试。让 Agent：

1. 搜索并读取相关代码。
2. 运行测试观察失败。
3. 精确修改实现。
4. 再次运行测试。
5. 用写入记录和成功测试记录作为凭证提交结果。

## 14. 开发顺序

1. 建立公开仓库并提交这些设计文档，形成设计先于源码的证据。
2. 实现数据类型、FakeModel 和最小 Engine。
3. 实现只读文件工具和路径边界。
4. 实现写工具、Shell、审批与凭证记录。
5. 实现真实 API、重试和上下文窗口。
6. 补齐压缩、终止检测和测试。
7. 运行相似性正式核查；命中红线则从规格重新实现相关模块。
8. 完成 README、视频和最终复测。

## 15. 答辩主线

答辩不强调“像某产品”，而强调三个可辩护决策：

1. **为什么不用 Agent SDK**：题目要求关键逻辑自研，显式六阶段循环更容易证明。
2. **为什么不声称 Shell 已沙箱化**：cwd 不是安全边界；MVP 选择审批、拒绝规则和诚实的能力声明。
3. **为什么设计完成凭证**：模型的自然语言结论不等于环境事实；引用真实操作记录可以减少“测试已通过”之类的幻觉。

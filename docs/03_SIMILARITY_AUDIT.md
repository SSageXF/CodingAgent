# 模块级相似性预审与正式核查方案

> 当前结论仅针对设计，因为 Agent 源码尚未产生。它不能替代实现完成后的逐文件核查，也不是法律意见。

## 1. 核查标准

本项目把以下情况视为需要处理的“模块级抄袭嫌疑”：

- 一个模块与参考仓库在职责切分、类型关系、控制流和异常语义上整体对应，只改了名称或语言。
- 连续复制或近似改写非平凡源码、注释、提示词、测试样例或 schema 描述。
- 将某仓库的核心类拆成几个文件，或把几个文件合并成一个类，但调用顺序和状态字段基本不变。
- 跨语言逐句翻译模块。

以下属于不可避免的通用功能，不单独构成嫌疑：

- 调用 LLM、维护消息、执行工具、读写文件和运行测试。
- 使用 JSON Schema、HTTP、重试、超时、退出码。
- 采用“模型调用 → 工具执行 → 结果回传”的基本循环。

判断重点是整体表达方式，不是是否存在同名的常见功能。

## 2. 风险等级

- **低**：只有领域通用功能相同，模块边界和实现机制明显不同。
- **中低**：借鉴了某个明确原则，但使用不同数据模型和控制流实现，需要在文档中注明来源。
- **中**：模块职责和流程与某仓库接近，编码前必须调整设计或准备充分独立性证据。
- **高**：存在整模块对应、连续文本/代码相似或跨语言翻译，必须删除并从需求规格重新实现。

## 3. 逐仓库设计级预审

### 3.1 openai/codex

**共同问题**：都有模型循环、工具路由、上下文、压缩、审批和本地执行。这是重合度最高的对照库。

**关键差异**：

- Codex 是 Rust monorepo，包含 Session/Turn/StepContext、ToolRouter/ToolRegistry、app-server、事件协议、多 Agent、插件和跨平台强沙箱。
- EvidenceCoder 是 Python 单进程 CLI，只有 Engine、RunBook、ContextWindow、Guard、Toolbox 和固定工具实现。
- EvidenceCoder 不建立客户端事件协议、工具动态发现、权限 Profile、world state 或 rollout。
- EvidenceCoder 的核心特色是 `CompletionReport` 引用 `OperationRecord`；不采用 Codex 的会话/工具生命周期表达。

**预审风险：中低。** 领域范围高度一致，但当前模块组织和核心数据模型不同。正式核查时需重点比较 Engine、ContextWindow、Guard 和 Toolbox，避免后来实现逐渐长成 Codex 的对应模块。

### 3.2 Aider

**共同问题**：读取仓库、修改文件、执行测试、控制上下文。

**关键差异**：

- 不实现 `Coder` 类族、Repo Map、Git 自动提交和编辑格式体系。
- `replace_text` 是 JSON 工具，不解析 Aider SEARCH/REPLACE 响应文本。
- 上下文来自 RunBook 投影，而不是 in-chat file 集合与 Repo Map。

**预审风险：低。** `replace_text` 的“精确旧文本替换”思想属于中低风险借鉴，工具参数、错误语义和实现必须独立编写。

### 3.3 mini-SWE-agent

**共同问题**：Python、循环、模型接口、命令执行、步数/时间限制。

**关键差异**：

- mini-SWE-agent 以 Bash-only 和线性 messages 为核心。
- EvidenceCoder 使用多个原生工具、六阶段循环、RunBook 投影与凭证完成协议。
- 不采用 Agent/Environment/Model 三分法和其异常/trajectory 格式。

**预审风险：中低。** 两者语言和规模接近，最容易出现无意的函数级相似；实现 Engine 和命令超时时不得参照其源码逐行编码。

### 3.4 OpenHands

**共同问题**：区分模型动作和环境结果，控制 Agent 生命周期。

**关键差异**：

- 不使用 Action/Observation 继承体系、AgentController、EventStream、Runtime 或 Server。
- RunBook 不发布事件，也没有订阅者；它只是 Engine 写入的数据集合。
- 不实现 Docker Action Executor。

**预审风险：低。** “意图与事实分离”是通用架构原则，但不得把 OperationRecord 扩展成 OpenHands 风格事件层。

### 3.5 Cline

**共同问题**：schema 工具、只读/写入审批、完成信号。

**关键差异**：

- 不依赖 Cline SDK，也不采用 shared/llms/agents/core 分包。
- 没有无状态 Agent 包与有状态 Core 的组合，没有 hub、session persistence 或插件。
- `submit_result` 的重点是凭证引用，不采用 `submit_and_exit/attempt_completion` 语义。

**预审风险：中低。** 工具组合看起来相近，但这些工具是 Coding Agent 的基本能力。需要用独立命名、schema、结果格式和测试证明并非模块复刻。

### 3.6 Goose

**共同问题**：原生 tool calling、错误回灌、输出控制、上下文修订。

**关键差异**：

- 不使用 Exchange、Extensions、Profile、Notifier 或 MCP。
- 不把工具作为动态扩展加载，工具表在代码中固定。
- 不实现多界面、多 Agent 或 ACP。

**预审风险：低。** 当前设计只采用了“错误也是观察”这一通用原则。

### 3.7 OpenCode

**共同问题**：循环、工具 registry、权限、精确编辑和上下文压缩。

**关键差异**：

- 不采用 TypeScript/Bun/Effect、SessionPrompt、Bus 或后台服务。
- 不实现 Agent 模式、子 Agent、ToolRegistry 服务或权限规则合并。
- Toolbox 是固定表和一次分派，不存在插件覆盖、作用域或动态注册。
- ContextWindow 从 RunBook 生成一次请求，不维护 OpenCode 式持久 Session 消息服务。

**预审风险：中低。** 工具与上下文领域最接近，正式核查需重点检查精确替换和上下文摘要实现。

## 4. 为降低相似性已经采取的设计约束

- 从空白目录开始实现，不 fork、vendor 或复制参考仓库。
- 不把参考仓库加入项目子模块或依赖。
- 不使用题目禁止的 Agent SDK，即使它们是开源的。
- 使用独立术语：Engine、RunBook、OperationRecord、ContextWindow、Guard、CompletionReport。
- 使用独立六阶段控制流，而非参考库的类/事件层级。
- 使用固定工具表，不实现插件或动态扩展架构。
- 系统提示词从题目要求和本设计稿重新撰写，不改写参考库提示词。
- 先提交设计文档，再提交源码，利用 Git 历史证明设计来源和演进。
- 在实现期间只回看本项目设计和 API 文档；若需再次查参考实现，必须在来源日志中记录原因和文件。

## 5. 实现后的自动核查

正式核查在功能冻结后、录制视频前执行。

### 5.1 固定参考版本

记录 7 个仓库实际比较的 commit SHA、分支、许可证和获取日期，避免比较结果随上游变化。

### 5.2 原文与代码片段扫描

- 比较源码、注释、docstring、提示词、JSON schema 描述和测试数据。
- 规范化换行与空白，但保留标识符。
- 任意连续 10 行非样板代码相同，或连续 50 个非平凡 token 相同，进入人工复核。
- 提示词连续 20 个实词相同即进入人工复核。

这一步必须覆盖所有语言，尤其能发现跨文件复制和提示词改写不足。

### 5.3 Token k-gram 模块相似度

- 去除纯格式、注释和常见 import 后生成 token 5-gram。
- 逐个 EvidenceCoder 模块与参考库文件计算 Jaccard/Cosine 候选相似度。
- 相似度达到 0.30 进入人工复核，达到 0.45 视为红线，除非能证明全是生成代码或标准协议样板。

数值只用于筛选，不能单独证明或排除抄袭。

### 5.4 Python AST 结构检查

对 Aider、mini-SWE-agent、OpenHands 中的 Python 文件：

- 解析 AST。
- 统一局部变量名和字面量。
- 对长度不少于 20 个语句节点的函数生成结构指纹。
- 归一化结构相似度达到 0.80 必须人工逐段解释；无法解释则删除并重写。

### 5.5 跨语言人工模块映射

Codex、Cline、Goose 和 OpenCode 不能只依赖文本工具。人工表格逐项比较：

- 状态所有者。
- 一轮调用的阶段顺序。
- 工具注册与分发。
- 审批发生位置。
- 历史写入和提示投影。
- 压缩触发与替换。
- 完成信号与失败恢复。

如果某个自研模块能与参考模块一一映射，且字段/调用顺序也高度一致，即使语言不同也要重构。

### 5.6 Git 来源审查

- 检查每个提交是否粒度合理并与设计阶段对应。
- 搜索参考项目名称、原类名、原工具名和许可证头是否意外进入源码。
- 确认没有大块一次性代码导入后再改名的提交。
- 保留 AI 辅助开发的事实，但确保作者能够解释每个模块和测试。

## 6. 人工复核处置

命中阈值后按以下顺序处理：

1. 标注相似部分及参考来源。
2. 判断是否仅为标准库/API 必需样板。
3. 若涉及核心控制流、状态、错误处理或提示词，不做简单改名。
4. 关闭参考源码，只依据本设计稿重新写该模块。
5. 增加针对自研行为的测试。
6. 重新运行全部相似性扫描，并在报告中保留前后结果。

## 7. 正式报告模板

实现后生成 `docs/05_FINAL_SIMILARITY_REPORT.md`，至少包含：

- 自研仓库 commit SHA。
- 7 个参考仓库 commit SHA。
- 扫描工具、参数和排除规则。
- 每个自研模块的最高相似候选。
- 所有阈值命中项及人工判断。
- 为降低相似性做过的重写。
- 尚不能自动排除的风险。
- 最终结论及审查人签字/确认时间。

## 8. 当前结论

当前设计没有发现“整模块照搬”迹象。最高风险来自与 `openai/codex`、mini-SWE-agent、Cline 和 OpenCode 共享的通用 Agent 问题，但 Proposed Design 已通过不同的数据模型、控制流和范围约束降低风险。

该结论是**有条件通过的设计预审**：只有实现后完成自动扫描、跨语言人工映射和 Git 来源审查，才能形成最终结论。
